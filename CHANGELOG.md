# Changes since TotkBits 0.0.9

User-visible additions and improvements in the current 1.0.1 codebase:

## Format inventory

| Category | Formats | Access |
| --- | --- | --- |
| New/upgraded text, YAML and JSON | **AINB**, **ASB/BAEV**, **XLink**, **ESETB/PTCL**, **BPHCL AAMP**, **BFEVFL**, **MSBT**, **Tag.Product** | Editable round trips; BFEVFL and Tag.Product use JSON, MSBT/MSYT use structured text, and the others use YAML. |
| New archive types | **ZIP**, **7z**, **BARS**, folder projects; nested **SARC/ZIP/7z/BARS** | Editable and saveable; RAR remains unsupported. |
| Native/in-process parsers | **AINB**, **ASB/BAEV**, **BFEVFL**, **MSBT**, **RSTB**, **ESETB/PTCL**, **BPHCL**, **HKCL**, **BPHHB**, **BFRES**, binary **FBX**, **BNTX**, **TexToGo**, **BWAV**, **AMTA**, **ZIP**, **7z**, **BARS**; XLink uses a native binding | No external Python/.NET conversion process. |
| New read-only/viewer formats | **HKCL**, **BPHHB**, BPHCL structure nodes, **BFRES**, binary **FBX**, **AMTA**, **TexToGo**, common raster images | BNTX/DDS are viewer-based but also provide targeted surface replacement; BNTX names are editable. |

## BPHCL physics merger

The Physics Merge workspace can copy selected cloth and collidable nodes between open BPHCL documents, validate compatibility, rebuild the target, and report added or skipped nodes. **HKCL → BPHCL** cloth import now materializes shared HKCL particle, constraint, skeleton and collider values through a compatible BPHCL template, rebuilds native ITEM/PTCH/AAMP data, and produces a saveable BPHCL; BPHCL → HKCL remains a validated graph preview.

## File formats and content tools

- Replaced the Python/.NET bridges with native Rust readers and writers for **AINB**, **ASB/BAEV**, **BFEVFL/EVFL**, and **MSBT/MSYT**. ASB retains/imports companion BAEV data; MSBT editing preserves labels, attributes, styles, encodings, endianness, and TOTK text tags.
- Added editable **XLink** (`.belnk[.zs]`) support with a dedicated Monaco language definition and syntax highlighting.
- Improved **ESETB** by exposing its embedded PTCL particle data as editable YAML and rebuilding it on save. **Tag.Product** parsing/writing now validates fields and tag references, rebuilds the bit matrix correctly, and preserves the binary rank table.
- Added native **RSTB** parsing/writing with search, add/edit/remove operations and original-compression preservation. BYML/BCETT, GameDataList, AAMP, SARC and other editable formats now restore the detected Zstandard dictionary or Yaz0 alignment when saved.
- Added physics tooling: hierarchical **BPHCL** browsing, editable AAMP leaves, node removal and BPHCL-to-BPHCL cloth/collidable merging. **HKCL** and **BPHHB** remain read-only source formats, while compatible HKCL cloths can now be imported and saved into BPHCL; BPHCL-to-HKCL uses validated graph previews with optional BPHHB-assisted bone mapping.
- Added read-only 3D workspaces for **BFRES**, MeshCodec **BFRES.MC**, and binary **FBX**. The React/Three.js viewer displays meshes, materials, resolved textures, bones, normals and UVs, with visibility, shading, brightness, section metadata and YAML controls.
- **Nintendo Switch Sports** BFRES 0.9 support: the viewer now reads the version 0.9 skeleton and material layouts (embedded textures resolve, one-bone shapes render), decodes shader options, render info and shader parameters into the material inspector, and reproduces the game's "insert color" skin/hair/outfit tint through the `*_Tcl` mask using the game's own colour tables. `Totkbits.exe --cli bfres_render <default|none|skin,hair,outfit> <input.bfres[.zs]> <output.png>` renders a BFRES headlessly with the same tint.
- Added Switch Toolbox compatible command-line editing for **BFRES** and **BNTX**: `Totkbits.exe --cli bfres_edit -i <in.bfres[.mc]> -o <out.bfres.mc> [--swap_int_name N] [--swap_model_name N] [--fbx m.fbx] [--rename_tex FROM TO]... [--totk_path <romfs>]` and `Totkbits.exe --cli bntx_edit -i <in.bntx[.zs]> -o <out.bntx[.zs]> [--swap_int_name N] [--rename_tex FROM TO]... [--replace_tex <image.png|.dds> [TEXTURE]]... [--export_tex DIR] [--astcenc <astcenc.exe>]`. Both use ports of the Toolbox loaders and savers (the BFRES v10 `ResFileSwitchSaver` with its implicit shader-parameter, bind-matrix and render-info rewrites, and the BNTX `BntxFileSaver`), plus Toolbox's own zstd/MeshCodec compression settings, so an open-and-save, rename or texture replacement produces the same bytes Toolbox writes; ASTC textures are encoded through an external `astcenc` when one is available. `--fbx` (with or without `--import_skeleton`) is now a port of Toolbox's own model replacement as well: the Assimp FBX import (per-corner expansion, multi-material split, `FlipUVs`/`Triangulate`/`GenNormals`/`JoinIdenticalVertices`/`LimitBoneWeights`), Toolbox's headless import settings (attribute set and formats, one buffer per attribute, material mapping by shape name, tangent/bitangent generation on the material's normal-map UV layer, `gsys_bake_st` reset), its bone lists, weight quantization, skinned bounding boxes and Syroot's vertex encoders (truncating half floats, `10_10_10_2` normals), with OpenTK's float math reproduced bit for bit; the output is byte-identical to the Toolbox CLI on every reference. The Items creator's custom weapon and armor FBX models go through the same path, so a generated model equals what Toolbox writes from the vanilla template in one pass.
- Added native **BPHSH** (TOTK Phive `hknpMeshShape` collision) support in `src-tauri/src/parser/physics/bphsh/`: a reader and writer that resave every vanilla `Phive/Shape/Dcc` file byte for byte (7132 of 7132), a port of the Havok mesh-shape builder (PhiveConverter's reimplementation, adjusted to TOTK's SDK 2022 output: whole-mesh sections, per-triangle interior bits, flat-convex quad encoding, the last vertex buffer's pad), and Wavefront OBJ + material JSON exchange using TOTK's own `PhiveConfig` material, user-shape-tag and layer names (`NoClimb`, `NoStick`, `Slip`, ...). `Totkbits.exe --cli bphsh_to_obj -i <in.bphsh[.zs]> -o <out.obj | dir>` and `Totkbits.exe --cli obj_to_bphsh -i <in.obj> -o <out.bphsh[.zs]> [--mat <materials.json>] [--no_weld] [--keep_order] [--max_error N]`. The builder's output is a fixed point of its own geometry (OBJ, shape, OBJ, shape gives the same bytes); rebuilding a vanilla shape from its OBJ reproduces its sections and primitives for most files but not its bytes, because the vanilla quantizer scales come from the pre-quantization source vertices and the quad pairing breaks ties by source index, neither of which the file records.
- Added **skeleton merging** from COLLADA (`.dae`) and binary FBX sources: `Totkbits.exe --cli merge_skeletons -o <out.fbx> <in.dae|in.fbx>... [--compare <reference.fbx>]` unions the bone hierarchies by name (first file's order first, later files' new bones appended under their parents, joints unused by any skin written as `Null` nodes, the way 3ds Max merges the same scenes) into a bones-only FBX 7400, and `--compare` reports parity with a reference skeleton (names, order, hierarchy, LimbNode/Null, transforms within tolerance). `bfres_edit --skeleton <a.dae> --skeleton <b.fbx>` pushes the merged skeleton into a BFRES: bones are re-ordered and added like Toolbox's "Import Bones", while the model's existing skinning palette and shape bone lists are kept and re-pointed at the new bone indices, so no FBX weights are needed.
- Items creator: armor `physics` accepts a **list of donor actors** (`"physics": ["Armor_005_Head", "Armor_180_Upper"]`; a single string still works). One usable donor is copied as before; two or more are **merged into one physics bundle named after the actor**: every cloth (with its paired skeleton) and every collidable of the donors' BPHCL files is merged into `Phive/Cloth/<actor>.bphcl`, their ClothParams into one `Phive/ClothParam/<actor>` (union of `CollidableList` and `MeshList`, `HktPath` renamed), and their ControllerSetParams into `Phive/ControllerSetParam/<actor>` with a single `ClothList`/`Cloth` entry, the concatenated `ClothReaction` list and every helper-bone file (`Default`, `Default_2`, …); `Component/Physics/<actor>` and the ActorParam `PhysicsRef` bind the merged set. Blank, unknown or duplicate donors are skipped; a failed merge fails the build. The Items Creator armor form has a `+`/`−` physics donor list. Custom FBX models with `replace_bones` may now skin to bones the template lacks (a merged skeleton with cape bones): the FBX skeleton is imported before the geometry replacement, unskinned `Null` joints such as `Root`/`Skl_Root` and wrapper nodes above them (a Blender armature object) are accepted, and template shapes the FBX supplies no mesh for are allowed to stay emptied.
- Items creator: a Zonai device can take a **collision OBJ** (`assets.physics_obj`, the form's *Collision (OBJ)* field; `physics_material` picks the Phive preset, `Material_Stone` by default). The mesh is split into convex pieces with **CoACD** (up to 40 pieces, each thinned to 40 vertices, the budget vanilla polytopes stay within) and written as the device's Polytope ShapeParam with the `AutoCalc` volume, centroid, inertia and bounds of every piece and of the whole; the rigid body's centre of mass follows the centroid, and the shape, rigid body (`<actor>_Body_0`), ControllerSetParam and PhysicsParam are renamed after the device. Convex pieces are what Ultrahand bonds and the Autobuild fans attach to, which a mesh collision never gets. CoACD runs through its C API from `bin/dlls/lib_coacd.dll`; without the DLL the option reports the missing sidecar and everything else keeps working.
- Items creator: the CoACD decomposition **can no longer crash or hang the app**. The upstream DLL let C++ exceptions cross into Rust (an instant abort: "Rust cannot catch foreign exceptions"), faulted on non-manifold meshes, and spun forever on a `nan` coordinate, which the OBJ parser accepted. `bin/dlls/lib_coacd.dll` is now the release build of the CoACD fork (https://github.com/SolidLink95/CoACD), which `repo_init.py` downloads like the other sidecars (a copy without `CoACD_runSafe` is replaced). The fork adds: its `CoACD_runSafe` validates the mesh and parameters (finite coordinates, in-range indices, a positive extent, threshold and resolution ranges), catches every C++ exception and allocation failure, and on MSVC turns access violations and other hardware faults into a status code with a message (`/EHa` plus a per-thread translator installed on the worker threads too); the legacy `CoACD_run` logs and returns an empty array instead of terminating, `CoACD_freeMeshArray` no longer leaks the outer array, and the DLL is built with the static CRT and std::thread instead of OpenMP, so it depends on nothing but kernel32. On the Rust side the mesh is validated before it reaches C++, the DLL is loaded once and never unloaded (unloading it while its worker threads existed crashed), CoACD's log is relayed to stderr through a callback, and the app runs each decomposition in a worker process (`Totkbits.exe --cli coacd_decompose -i request.json -o pieces.json`), so even a fault the library cannot intercept (a TBB worker thread, heap corruption, an exhausted stack) only kills the worker and comes back as "the CoACD worker process crashed (exit code 0x…)". The same subcommand works by hand: `Totkbits.exe --cli coacd_decompose -i <mesh.obj> -o <pieces.obj|pieces.json> [--threshold N] [--max_hulls N] [--prep_res N] [--no_preprocess] [--no_merge] [--seed N]`. An upstream DLL without `CoACD_runSafe` is refused with a message pointing at the rebuild. The fork also adds a cooperative **time limit** (`CoACD_Params.time_limit_seconds`, checked between the search and merge steps): a self-intersecting mesh decomposed with preprocessing off, which ran for hours, now stops with "time limit exceeded"; the items creator allows 30 minutes per collision mesh and the CLI takes `--time_limit SECONDS`.
- Items creator weapons: `weapon_parameters.indestructible: true` (form checkbox **Indestructible**, default off) writes `InitInvincibilityType: InvincibleNoDamageReaction` into the actor's `Component/LifeParam` file so the item never loses durability; the Durability field is hidden and `max_life` ignored while it is set. The **Shield bash damage** field is shown only for shields, and a shield template now gets the value written (`ShieldBashDamage` is added to its AttachmentParam and `AttachmentShieldBashDamage` to its RSDB row) instead of being dropped.
- Items creator **Zonai** tab: clones a vanilla Zonai device together with its capsule (the pouch item) under new names. The base list is every device PouchActorInfo names as a `CapsuleContent`, shown with its capsule icon (decoded from the RomFS into `.cache/zonai` on first use). Every scalar of every BYML entry of the device pack is editable in a file/value browser (`$parent`-inherited values included, inserted with their container when changed); the ActorParam and every edited entry are renamed after the new actor (an edited shared entry such as `Life/LifeParameters/SpObj_Weapon_A` too, so the change stays private to it) and the references between them follow, while unchanged entries keep their vanilla names the way the game's own derived actors do (a renamed but unchanged copy of the `BlackboardParamTable/BeamosBeam` a shooter and its beam share left the cloned beam unable to fire). A companion whose ID equals its template is the vanilla actor **edited in place** (pack rewritten under its own name, RSDB rows updated, nothing renamed): the Beam Emitter's native logic fires nothing but the vanilla `BeamosBeam` (a renamed copy, or any other beam actor, never fires), so a custom beam has to be that actor itself, at the price of every Beam Emitter in the game showing it. Actors the device references (a cannon's projectile) can be cloned as *companions* with edits of their own, the device being redirected to the clone. Optional custom model (`.bfres`/`.bfres.mc`, or an FBX geometry replacement), capsule and device icons, fuse adjective, shop sale of the capsule; RSDB ActorInfo/GameActorInfo/PouchActorInfo rows and Tag entries are cloned (`ActorName` names the clone, `MaxLife` follows the edited life parameters), pouch and attachment labels and `IsGet` flags are written, and the mod's single RSTB pass covers it. Spec entries carry `kind: "Zonai"` (`--cli create_weapon` accepts them in the same JSON list; `params` are keyed by template entry path and dotted value path). The device and each companion take an optional **chemical donor** (`chemical`, form field *Chemical donor*): the vanilla actor's `Chemical/*` and `Component/ChemicalParam/*` entries are copied into the clone's pack and its ActorParam `ChemicalRef` pointed at them, so a beam cloned from `BeamosBeam` with `"chemical": "Drake_Beam_Small_Fire"` burns what it hits. A `params` path naming a whole list of scalars now takes a JSON list (`"AttackParams[0].DamageElements": ["Fire"]`), typed after the list's existing elements. A Zonai device now always gets a model file of its own like a weapon (`Model/<project>.<actor>.bfres.mc`, the template model renamed after the device unless a custom BFRES/FBX is given), and the ActorInfo rows of the device and its companions follow their packs: `FmdbName`, the `ELinkUserName`/`SLinkUserName` the pack's link parameters declare (a companion with a custom ELink user was still listed under the vanilla user), and, with a chemical donor, an `InstanceHeapSize` at least as large as the donor's. The device's `RSDB/AttachmentActorInfo` row (the special-parts registration: create priority, fuse data, and the capsule the device returns to, now the new capsule) is cloned too; without it a custom device could be bought but not taken out of the pouch. The device takes an optional **Autobuild cost** (`autobuild_cost`, default 3 in the form, blank keeps the template's): the zonaite Autobuild charges for it, written the way `Obj_AirPlatform` prices its sky platform at 100, as a `GameParameter/AutoBuilderReplacementParam` entry holding `OverwriteConsumptionNum` and referenced from the device's GameParameterTable (both renamed after the device; a table the template keeps outside its pack is copied in first).
- Items creator **Language** select: the item names and descriptions go into the Mals archive of the chosen language (every `Mals/<Lang>.Product.*.sarc.zs` of the RomFS is listed; US English is the default, else EU English, else the first archive). CLI: `--cli create_weapon … --lang EUen`.
- Items creator: armor specs accept `"armor_effects": ["QuietnessUp", {"type": "DecreaseZonauEnergy", "level": 1}]` (form section **Armor effects**, a `+`/`−` list with icons): the entries replace the ArmorParam `ArmorEffect` list and the first one becomes the PouchActorInfo `ArmorEffectType`; the choices are every `ArmorEffectType` found in the RomFS base armor packs.
- Items creator: Great Fairy upgrade **ingredients are chosen from a list** instead of typed: each rank takes up to three ingredients (the first one required) with a count, picked with icons from every pouch item a vanilla EnhancementMaterialInfo row asks for (173 distinct items, live fish/plants and their `Item_*Get` pick-up forms merged through the ActorInfo `ActorName` redirect). The icons are decoded from the RomFS `UI/Tex/Icon` BNTX files on first use into `.cache/ingredients/<actor>.webp` (128 px), next to the base icons' `.cache/webp`; the catalog carries the list as `ingredients` and `item_creator_ingredient_icons` serves the pictures.
- Items creator: a **Generate RSTB** checkbox (default off since TKMM rebuilds the table itself; the CLI still generates one unless `--no_rstb` is given) next to the shop selector; **Import JSON…** now also sets the output folder to the spec file's folder, so the mod lands next to its spec; unticked, the mod is written without a ResourceSizeTable pass (for TKMM or a later `--cli create_weapon --rstb_only`) and the summary says so. The CLI equivalent is `--cli create_weapon … --no_rstb`; the report's `rstb` block is then absent.
- Items creator: the shop picker gained a **Bargainer Statue** entry (spec `"vendors": [{"actor_name": "BargainerStatue", "buying_price": 300, "quantity": 1}]`). The item is added to the poe trade list (`DemonStatue_Shop` ShopParam) of every statue at once: the six `TwnObj_DemonStatue_C_01`..`C_06` packs and the Lookout Landing `FldObj_AmosStatue_A_02`, which share one stock in vanilla. Entries are written with `Currency: MinusRupee`, `PriceOffset: 0` (the statue charges the PouchActorInfo `BuyingPrice`, so the form's buy price is the poe price) and both `ReleaseRequirements` checks off, so the item is on sale from the start regardless of story progress instead of the vanilla buy-back rule. Beedle entries are unchanged.
- Added a command-line **TexToGo image replacer**: `Totkbits.exe --cli txtg_edit -i <in.txtg[.zs]> -o <out.txtg[.zs]> --png <image.png> [--astcenc <astcenc.exe>]` (aliases `txtg`, `--txtg`) swaps the pixels of a `.txtg` texture for the PNG while keeping the file the same kind of texture: the format code, mip count, format settings, component selectors, texture settings and hash are preserved and every mip is re-encoded in that format (BC1/BC3/BC4/BC5/BC7 natively, ASTC 4x4 and 8x8 through ARM's astcenc, found in `bin/cpp`, `ASTCENC` or `--astcenc`). An output ending in `.zs` is Zstandard-compressed. The ASTC block footprint of a `.txtg` is read from the header (low byte of the second texture setting, one nibble per axis holding the block size minus one), which also fixes the image viewer: `0x102`/`0x105` textures such as `Armor_171_Belt_Alb` are ASTC 4x4, not 8x8, and `0x106` ranges from 4x4 to 12x12.
- ASTC textures are now **encoded in process** through ARM's astcenc 5.7.0 core codec as a shared library (`bin/dlls/astcenc-avx2-shared.dll`, or `astcenc-sse4.1-shared.dll` on CPUs without AVX2; `ASTCENC_DLL` overrides the location) instead of spawning the `astcenc-*.exe` command line per mip level with PNG/ASTC exchange files in a temp folder. The library is driven with the same profile (`-cs`/`-cl`), `-thorough` preset, swizzle and per-core threading as the executable, and its blocks were verified byte-identical against the 5.7.0 executable on the icon and TexToGo corpora (1070 encodes over five block footprints, both profiles, odd crops and full mip chains). `repo_init.py` downloads the DLLs into `bin/dlls`; `--astcenc <exe>` of `bntx_edit` and `txtg_edit` now takes the DLL. The TexToGo replacement pipeline moved out of the CLI into `tools/txtg_edit.rs` (`replace_from_paths` / `encode_replacement`), so the Items Creator's dye slices and the command line share one implementation; `txtg_edit` is a thin wrapper around it.
- Saving a BPHCL that was opened from inside a pack no longer replaces the parent pack's file tree with the BPHCL's node list; the parent keeps its tree and the saved `.bphcl` entry is marked modified in it.
- Physics Merge: a **BPHCL can be saved again** after "Merge selected" (and after any other BPHCL edit). The frontend still listed BPHCL among the read-only formats from before BPHCL editing existed, which hid **Save** / **Save as** for BPHCL documents although the backend writes them (to disk, under a new name, or back into the parent pack).
- Items creator: armor **upgrade ranks no longer build their own icons**. Vanilla ranks (`Armor_002_Head` on `Armor_001_Head`) ship pixel-identical copies of the base icons under the rank's name, because the game loads `UI/Tex/Icon/<actor>[_<Color>].bntx.zs` by actor name and the only redirect, `ActorInfo.ActorName`, also merges the pouch identity. The base piece is the only one whose icons go through PNG decoding, dye tinting and ASTC encoding; each rank's 1 or 16 files are byte clones of the base's finished BNTX with just the texture name renamed, so a four-rank dyeable piece encodes 16 icons instead of 80.
- Items creator: loading a spec JSON sets the **Mod name** to the file's stem (`MyCape.json` → `MyCape`).
- Items creator: each armor physics donor can be an **actor pack file** as well as a vanilla actor: `"physics": ["Armor_005_Head", "C:\\mods\\Cape\\Armor_950_Head.pack.zs"]` reads the second bundle (its `Phive/*`, `Component/Physics/*` and `PhysicsRef`, actor named by the pack's ActorParam) from disk, so a piece from another mod can donate or take part in a merge. The armor form's physics list has a per-donor source switch: **Base armor** (picked like the template from every vanilla base armor whose pack carries `Phive/Cloth` files, any slot; the catalog exposes this as `cloth`), **Pack file** (Browse… for a `.pack.zs` / `.pack`) or **Actor name** (a plain text field; an empty name or one without an actor pack in the RomFS is skipped and the template keeps its own physics).
- Items creator: armor specs accept `"helper_bone": "<vanilla armor actor>"` (aliases `helper_bones`, `helper_bone_actor`; form field **Helper bones**, picked like the template from every base armor whose pack carries `Phive/HelperBone` files, any slot). After the physics step (donor copy, merge or the template's own files) the chosen actor's `Phive/HelperBone/*` files replace the ones the piece has, renamed `Phive/HelperBone/<actor>.bphhb` (`<actor>_2`, … for several), the ControllerSetParam `HelperBoneList` points at them and the ControllerSetParam, `Component/Physics` and ActorParam `PhysicsRef` are renamed after the actor; a template without physics of its own (the shared `Dummy` PhysicsParam) gets a helper-bone-only controller set like vanilla `Armor_008_Upper`. A donor without helper bones fails the build.
- Items creator: merging two or more armor physics donors now produces the same pack layout as a hand-made merge (checked against vanilla `Armor_999_Head` + `Armor_225_Head`): only the **first donor's helper bones** are kept, renamed `Phive/HelperBone/<actor>.bphhb` (`<actor>_2`, …) with the `HelperBoneList` re-pointed at them, while the other donors' helper-bone files and entries are dropped (they drive bones of those donors' own models, e.g. the hat's `Hat_1_Armor`, which the merged actor does not have; `helper_bone` still picks a set explicitly). The merged ControllerSetParam also unions the donors' `ClothAdvandecOption` lists, so no `Phive/*` file keeps a donor's name any more.
- SARC: **Tools ▸ Add folder** (and the root-level context menu) adds the chosen folder at the archive root again. The entries were joined as `/<folder>/...`, so the tree showed them under a folder with an empty name.
- Items creator: armor specs accept `"skin_material": "<vanilla armor actor>"` (form field **Skin material**, picked like the template): the chosen actor's ArmorParam `HiddenMaterialGroupList` (the body-skin materials the piece hides) is copied into the new piece; the template picker also gained a **Hide upgrades** checkbox (on by default) that hides Great Fairy rank actors.
- Items creator: armor pieces can now be **upgradeable at the Great Fairies** and **dyeable**. Upgrades are on by default (`"upgrades_enabled": true`, alias `enable_upgrades`); an armor spec may list up to four `upgrades` (`{"defense", "rupees", "materials": [{"actor", "count"}], optional "actor_name", "buying_price", "selling_price", "activate_set_bonus"}`, `upgrades[0]` being ★), and an empty list copies the template's vanilla chain (or the Hylian chain with +2/+5/+9/+17 defense when the template has none). The generator writes the vanilla rank layout: the base ArmorParam gains `NextRankActor` and the rank-2 cost, and every rank becomes its own actor pack (`<actor>_1` … `<actor>_4` by default, e.g. `Armor_900_Head_1`) that inherits the base via `$parent` with its `Rank`, `BaseDefense`, `NextRankActor`, EnhancementMaterial (cost to the next rank) and PriceParam, plus ActorInfo/GameActorInfo/PouchActorInfo (`ArmorRank`, `ArmorNextRankActor`) and Tag rows, EnhancementMaterialInfo rows, GameData flags, pouch labels and the icons per rank. The Great Fairy event flows only read `GreatFairy_ArmorRank`, so no NPC data changes are needed. `"dyeable": true` (alias `make_dyeable`, off by default) turns a single-colour template into a dye-shop piece: the pack gets the slot's `ColorVariationRef` component and `ModelVariationAnims`, the PouchActorInfo rows get `ColorVariationType: ArmorDye`, every `_Alb` TexToGo texture is written as sixteen `_Alb.0` … `_Alb.15` slices (slice 0 untinted, the model re-pointed at `_Alb.0`), a `Model/<project>.anim.bfres.zs` with the `<Slot>_ftp` texture-pattern animation is generated through the new FMAA writer (byte-identical to the vanilla animation files), and the fifteen tinted icon variants are produced for the base and every rank. A template that is dyeable already keeps its vanilla `Model/<project>.anim.bfres.zs`: the file is byte-patched when the new project name has the same length, and otherwise (e.g. `Armor_1091` → `Armor_760`) its texture-pattern animations are read, renamed and rewritten through the same writer, so the dye animation is no longer silently missing for such names; pieces of one project generated together merge their slot animations into the one file. The template info exposes a vanilla piece's upgrade chain, and the Items Creator form has a "Make dyeable" switch and a Great Fairy upgrades section (enable switch, per-rank editor, "Use template's upgrades" shortcut).
- Items creator: weapon and armor specs accept `"sound"` (alias `"audio"`) and `"effect"` **donor actor names** (form fields **Audio** and **Effect**, plain text): the donor's `Component/SLink` / `Component/ELink` file is copied into the new pack as it is (it keeps the donor's `UserName`, so the donor's sound and effect resources apply), it replaces the template's own link file, the ActorParam `SLinkRef` / `ELinkRef` binds it and the RSDB ActorInfo row's `SLinkUserName` / `ELinkUserName` names the donor's link user (weapons and armor, the same way vanilla rows mirror their own link files); upgrade ranks inherit it. Armor also takes the audio keys of the donor's ArmorParam (`SoundMaterial`, `HasSoundCloth`, `IsBarefootSound`) and the effect keys (`WindEffectMesh`, `WindEffectScale`). A blank name, or one without an actor pack or that link component in the RomFS, is skipped and the template's own sound / effect stays. Weapons still accept the tagged `{"source": "file", "path": ...}` form.
- Items creator: weapon and armor specs accept `"effect_keys": ["古代矢完成", "軌跡"]` (aliases `xlink_keys`, `effect_ai_keys`; form checkbox **Advanced effect**, off by default, which reveals an **XLink keys** field). It reproduces the trick hand-made mods use for a permanent glow, trail or gloom: the item gets a root AI, `AI/<actor>_Effect.root.ainb` with one `OneShotXLinkSearchAndEmit` node per key (several keys under an `Element_Simultaneous` root) and `AI/AIInfo/<actor>_Effect.engine__actor__AIInfo.bgyml`, bound by a new ActorParam `AIInfoRef`; any root AI the template had is replaced.
